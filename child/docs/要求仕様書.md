# 要求仕様書
## エッジAI機械視覚システム（Raspberry Pi Zero 2W + IMX500）

**文書番号:** REQ-001
**作成日:** 2026-02-23
**バージョン:** 2.33
**改訂日:** 2026-06-26
**対象ソフトウェア:** Picamera.py / web_server.py / index.html

---

## 1. 目的と適用範囲

本仕様書は、Raspberry Pi Zero 2W と IMX500 ニューラルプロセッサを搭載したカメラモジュールを用いて、リアルタイム物体検出・信号灯認識を行うエッジAI機械視覚システムの要求仕様を定める。

本システムは工場・設備の監視用途を主対象とし、Webブラウザからのリモート制御・監視に加え、SPI LCDとタッチパネルによるローカル操作にも対応する。

---

## 2. システム構成

### 2.1 ハードウェア構成

| 項目 | 仕様 |
|------|------|
| 計算機 | Raspberry Pi Zero 2W |
| カメラ | Raspberry Pi カメラモジュール（IMX500 ニューラルアクセラレータ内蔵） |
| センサーサイズ | 4056 × 3040 画素（物理） |
| ディスプレイ出力 | HDMI（任意接続） |

| タッチパネル | XPT2046 抵抗膜式（ハードウェアSPI, SPI0 CS1, IRQ=GPIO17） |
| ストレージ | MicroSDカード |

## 3. 機能要件

### 3.1 推論モード

システムは以下の2つの推論モデルを切り替えて使用できること。

| モデルID | モデル名 | 検出対象 | ラベル数 |
|---------|--------|---------|---------|
| `object_detection` | 物体検出モデル | COCO標準80クラス（人・車・動物・家具 等） | 80 |
| `signal_tower` | シグナルタワー | 信号灯の色クラス直接分類（赤・黄・緑・青・白・消灯） | 5〜6 |

- モデルファイル形式: `.rpk`（Raspberry Pi Kernel形式）
- 推論解像度: 640 × 640（固定）
- 推論フレームレート目標: 15 FPS

### 3.2 カメラ制御

#### 3.2.1 解像度・クロップ制御

| 要件ID | 要件内容 |
|-------|---------|
| CAM-01 | カメラ出力解像度として 480×320 / 640×480 / 640×640 / 1280×720 / 1920×1080 を選択できること |
| CAM-02 | FHD・640×640モードとも、画角（センサークロップ）を固定ステップ（10 / 12 / 17 / 24 / 34 / 49 / 70 / 100 %）で動的に変更できること（カメラ再起動不要） |
| CAM-03 | クロップは中心基準で行い、ScalerCrop コントロールにより即時反映されること |
| CAM-04 | ScalerCropは出力解像度のアスペクト比に合わせること（歪みなし）。推論ROIは全モードで正方形（センサー高さ基準、センサー中央）とすること |
| CAM-05 | FHD（1920×1080）モードではHDMIオーバーレイを1/2スケール（960×540）に縮小すること |

#### 3.2.2 カメラ出力解像度切り替え

| 要件ID | 要件内容 |
|-------|---------|
| CAM-RES-01 | カメラ出力解像度を FHD（1920×1080）と 640×640 の2種類からWebで切り替えられること |
| CAM-RES-02 | 解像度設定は `recognition_config.json` の `camera_resolution` キーに永続化されること |
| CAM-RES-03 | 解像度変更後はプロセスを再起動してカメラを再設定すること |
| CAM-RES-04 | 解像度切り替え中はモデル切り替えと同じローディング表示（最大120秒）を行うこと |

#### 3.2.3 起動・再起動

| 要件ID | 要件内容 |
|-------|---------|
| CAM-06 | カメラ起動失敗時は最大5回リトライし（間隔3秒）、全失敗時は終了すること |
| CAM-07 | 認識ON→OFFへの切り替えはカメラ再起動不要とすること |
| CAM-08 | 認識OFF→ONへの切り替えはIMX500ファームウェア再転送のためプロセス再起動とすること |
| CAM-09 | モデル変更後はプロセスを再起動してモデルをリロードすること |

### 3.3 推論・検出処理

#### 3.3.1 検出後処理

| 要件ID | 要件内容 |
|-------|---------|
| DET-01 | 検出信頼度スコアが閾値（デフォルト0.25）以上の結果のみを有効とすること |
| DET-02 | 閾値は0.25〜0.95の範囲でWeb UIから動的に変更できること |
| DET-03 | 物体検出・シグナルタワー検出ともにNMSを適用しないこと（重複検出許容） |
| DET-05 | nanodet形式とYOLO11n MultiClassNMS後処理済み形式の両方に対応すること |
| DET-06 | バウンディングボックスの可視領域がディスプレイ幅の1%未満の場合は表示をスキップすること |

#### 3.3.2 点灯/点滅判定（シグナルタワー）

| 要件ID | 要件内容 |
|-------|---------|
| ST-01 | 各色の検出有無を直近45フレーム（3秒分、推論15FPS基準）分の履歴として保持すること |
| ST-02 | 45フレーム分のバッファが満杯になった後、未検出フレームが20%超の場合「BLINK」、20%以下の場合「ON」と判定すること。バッファ蓄積中（45フレーム未満）は「ON」と表示すること |
| ST-03 | 判定結果を検出枠の左外に表示すること（英語表記: ON / BLINK） |
| ST-04 | 信頼度スコアを検出枠の右外に表示すること |
| ST-05 | 点灯/点滅の履歴更新は毎フレーム行うこと（1秒ごとではなく） |
| ST-06 | バッファ蓄積中（45フレーム未満）のCSVログ状態は「off」とすること |

#### 3.3.3 シグナルタワーID領域設定

| 要件ID | 要件内容 |
|-------|---------|
| STID-01 | Web UI・タッチの「ID設定」操作後、3秒間の検出位置を収集してから長方形領域を確定・設定すること（点滅ライトの消灯フレームを挟んでも確実に位置を捉えるため） |
| STID-02 | クラスタリング条件: X方向距離が平均検出枠幅以内、かつY方向距離が平均検出枠高さの5倍以内の検出を同一クラスタとすること |
| STID-03 | 全ID枠は同一サイズ（幅W・高さH）とし、各クラスタ中心を基準とした非重複最大矩形を設定すること。W・Hの決定方法: 全クラスタペアについて \|ΔX\| ≥ \|ΔY\| のペアはX方向で分離（W ≤ \|ΔX\|）、\|ΔY\| > \|ΔX\| のペアはY方向で分離（H ≤ \|ΔY\|）とし、W = min(X制約, デフォルト:画幅)、H = min(Y制約, デフォルト:画高)。各枠: cx = クラスタX中心、x_half_width = W/2、y_top = cy − H/2、y_bottom = cy + H/2（画面端でクランプ）。IDはX昇順・Y昇順で 1, 2, 3, … を付与すること |
| STID-04 | 設定されたID枠と番号をHDMI・Web配信映像にオーバーレイ表示すること |
| STID-05 | ID領域設定は `/home/pi/signal_regions.json` に永続化し、再起動後も保持すること |
| STID-06 | ID設定ボタンはシグナルタワーモデル使用時のみ表示すること |
| STID-07 | Web UI・タッチの「IDリセット」操作で、設定済みID領域を全削除できること |
| STID-08 | 同一ID枠内で同じ色が複数検出された場合、信頼度スコアが最高のものだけを採用すること（描画・ログともに対象）。ID枠外（region_id=0）の検出はフィルタ対象外とすること |

#### 3.3.4 ID名前管理

| 要件ID | 要件内容 |
|-------|---------|
| IDNAME-01 | シグナルタワーの各ID番号に対して、ユーザーが名前（ラベル）を3項目（名前1・名前2・名前3）に分割して付与できること |
| IDNAME-02 | ID名前のマッピング情報をサーバー側のJSONファイル（`/home/pi/id_names_config.json`）に永続化し、再起動後も保持されること。各IDの値は3項目の文字列配列（`["名前1", "名前2", "名前3"]`）とする。旧形式（単一文字列）は `["旧名", "", ""]` として後方互換に読み込むこと |
| IDNAME-03 | Web UIの「ID 名前一覧」テーブルでID番号と3項目の名前を表示し、各行の名前1・名前2・名前3欄をそれぞれテキスト入力で編集できること |
| IDNAME-04 | ID番号を新規追加できるように、ID入力フィールドと「＋追加」ボタンを用意すること |
| IDNAME-05 | 名前欄の削除ボタンで該当IDのエントリを削除できること |
| IDNAME-06 | シグナルタワーモードの変化ログで、ID列に「ID (名前)」形式で表示すること（名前が設定済みの場合）。名前は3項目を空項目を除きスペース連結したものとすること |
| IDNAME-07 | 名前変更・追加・削除の操作はブラウザのどのクライアントからでも即座にサーバーに反映され、他のクライアントでもリアルタイムに同じ名前が表示されること |

| 要件ID | 要件内容 |
|-------|---------|
| DISK-01 | `/home/pi` の空き容量が1GB未満の場合、`/home/pi/images/`・`/home/pi/raw_images/`・`/home/pi/logs/` 内のファイルを更新日時の古い順に空き容量が1GB以上になるまで削除すること |
| DISK-02 | ディスク空き容量チェックおよびクリーンアップはバックグラウンドスレッド（SaveWorker）で行い、メインスレッドをブロックしないこと |
| DISK-03 | クリーンアップ実行は60秒に1回に制限し、連続削除を防止すること |

| DISK-05 | クリーンアップ実行時はコンソールに削除ファイルパスと削除後の空き容量を出力すること |
| DISK-06 | 空き容量に依存せず、`/home/pi/raw_images/` は最新 `MAX_RAW_IMAGES`(=3000) 枚、`/home/pi/images/` は最新 `MAX_RESULT_IMAGES`(=3000) 枚を上限とし、超過分を古い順に自動削除すること。判定はファイル名先頭のタイムスタンプ順で行い、大量の`stat`呼び出しを避けてSD I/O負荷を最小化すること。実行はSaveWorker内で`FILECAP_INTERVAL`(=60秒)間隔とすること。1回あたりの削除は `FILECAP_MAX_DELETE_PER_RUN`(=300) 件までに制限し、初回の大量削除がSDを飽和させてweb_serverを巻き込むのを防ぐこと（超過分は次回以降に段階的に削除） |

### 3.6 CSVログ

#### 3.6.1 物体検出ログ（`log_object_detection_YYYYMMDD.csv`）

| カラム名 | 内容 |
|---------|------|
| 日時 | YYYY-MM-DD HH:MM:SS |
| 物体名 | 検出クラス名 |
| X | バウンディングボックス左上X座標（ピクセル） |
| Y | バウンディングボックス左上Y座標（ピクセル） |
| 幅 | バウンディングボックス幅（ピクセル） |
| 高さ | バウンディングボックス高さ（ピクセル） |
| スコア | 信頼度スコア（小数点2桁） |

#### 3.6.2 シグナルタワーログ（`log_signal_tower_YYYYMMDD.csv`）

| カラム名 | 内容 |
|---------|------|
| 日時 | YYYY-MM-DD HH:MM:SS |
| ID | シグナル領域ID（未設定時は `-`） |
| 中心X | 検出領域中心X座標 |
| 中心Y | 検出領域中心Y座標 |
| 色 | 検出色名（red/yellow/green/blue/white） |
| 状態 | 点灯 / 点滅 |

- 点灯/点滅判定: 直近45フレーム（3秒分）のバッファが満杯になった後、未検出が20%超の場合は「点滅（blink）」、20%以下の場合は「点灯（on）」とする。バッファ蓄積中（45フレーム未満）は「消灯（off）」とする
- ログファイルはモデルタイプ別・日付別に分けて作成すること

#### 3.6.3 変化ログ（`log_changes_<model_type>_YYYYMMDD.csv`）

シグナルタワー変化ログ（`log_changes_signal_tower_YYYYMMDD.csv`）:

| カラム名 | 内容 |
|---------|------|
| datetime | YYYY-MM-DD HH:MM:SS |
| id | シグナル領域ID |
| color | 色名（red/yellow/green/blue/white） |
| old_state | 変化前の状態（on/blink/off） |
| new_state | 変化後の状態（on/blink/off） |

物体認識変化ログ（`log_changes_object_detection_YYYYMMDD.csv`）:

| カラム名 | 内容 |
|---------|------|
| datetime | YYYY-MM-DD HH:MM:SS |
| label | 検出クラス名 |
| event | detected（検出開始）または lost（消失） |

- 状態変化が発生したフレームのみ記録すること（毎フレーム記録しない）
- 消灯（off）判定・物体消失判定には2秒のデバウンスを適用すること（一時的な未検出で即記録しない）

#### 3.6.4 送信用ログ（`<IP>_<YYYYMMDD>.csv`）

外部システムへの送信を目的とした、シグナルタワーの状態コードログを生成すること。

| 要件ID | 要件内容 |
|-------|---------|
| SEND-01 | 送信用ログファイルを `/home/pi/send_logs/` に1日ごとにローテーション作成すること。ファイル名は `T1_<IPアドレス>_<YYYYMMDD>.csv` 形式（日付はローカル日付）とし、同一日のログは同一ファイルへ追記すること。IPアドレス中の `.` は `-` に変換すること（例: `T1_192-168-1-5_20260623.csv`） |
| SEND-02 | ファイルの各行は `日時(YYYYMMDDhhmmss),名前1,名前2,名前3,状態コード` の5カラム（ヘッダー行なし）とすること。名前1〜3は当該IDに登録された3項目を別々の列に出力すること |
| SEND-03 | 対象は `id_names_config.json` で名前が設定済み（3項目のうち1つでも空文字でない）のIDすべてとし、名前1〜3列には当該IDの登録3項目をそれぞれ出力すること |
| SEND-04 | 状態コードは、当該IDのシグナルタワー各色の点灯/点滅状態（on/blink/off）の組み合わせから、状態コード定義（`status_code_config.json`）のパターン照合により決定する数値とすること |
| SEND-05 | 各IDの状態コードが変化したときのみ行を追記すること。日付が変わって新しい日次ファイルへ切り替わった直後は全対象IDの現在の状態コードを初期行として書き出すこと |
| SEND-06 | 状態コード定義はパターンの配列とし、各パターンは色ごとの条件（on/blink/off、未指定の色は判定対象外）と適用コード、および任意の備考（`note`、自由記述）を持つこと。パターンは先頭から順に評価し、条件をすべて満たす最初のパターンのコードを採用すること。どのパターンにも一致しない場合はデフォルトコードを採用すること。備考は判定には使わず、設定の覚書として保持・表示するためのものとすること |
| SEND-07 | 状態コード定義は `/home/pi/status_code_config.json` に永続化し、Web UIから編集できること。編集内容は推論側が5秒以内に再読込して反映すること |
| SEND-08 | 送信用ログの記録はシグナルタワーモデルかつ認識ON時のみ行うこと |

状態コード定義ファイル（`status_code_config.json`）の形式:

```json
{
  "patterns": [
    {"conditions": {"red": "on", "green": "on"}, "code": 5, "note": "稼働中"},
    {"conditions": {"yellow": "blink"}, "code": 7, "note": "警告"}
  ],
  "default": 0
}
```

#### 3.6.5 送信用ログのMQTT送信

`/home/pi/send_logs/` 内の送信用ログCSVの各行を、Webで設定したMQTTブローカーへ送信（publish）すること。送信形式は `child-csv-to-mqtt.py` に準拠したJSONとすること。

| 要件ID | 要件内容 |
|-------|---------|
| MQTT-01 | 送信先設定（自動送信の有効/無効、ブローカーIP（host）、ポート、トピック、ユーザー名、パスワード、自動送信間隔）を `/home/pi/send_target_config.json` に永続化すること。デフォルトは `enabled=false, port=1883, topic=presence/record, username="", interval=600` とすること |
| MQTT-02 | 送信は `paho-mqtt` で行うこと。ユーザー名が設定されている場合のみユーザー名/パスワード認証を行うこと。`paho-mqtt` 未インストール時はエラー文言を返すこと（`pip install paho-mqtt` が必要） |
| MQTT-03 | `send_logs` 内の全 `*.csv` を対象とし、ファイル内のデータを1行ずつ、設定トピックへ個別のMQTTメッセージとして送信（QoS=2）すること。送信形式は `child-csv-to-mqtt.py` 互換のJSONとし、CSV1行（`YYYYMMDDhhmmss,STA_NO1,STA_NO2,STA_NO3,T1_STATUS`）を `{event_id, mk_date, sta_no1, sta_no2, sta_no3, t1_status, device_id, schema_version}` に変換して送ること。`event_id` は `device_id|mk_date,sta_no1,sta_no2,sta_no3,t1_status` のSHA1（16進）として決定的に生成し、同じ行の再送でも受信側で二重記録されないようにすること。`device_id` は環境変数 `DEVICE_ID`（無ければホスト名）、`schema_version` は1とすること。`t1_status` は整数。形式不正な行（フィールド数≠5、日時が14桁数字でない、状態が非整数）はスキップし、再処理しないよう送信済み行数は進めること。書き込み途中の不完全な行（末尾が改行で終わらない最終行）は確定するまで送信しないこと |
| MQTT-04 | ファイルごとの送信済み行数を `/home/pi/send_target_state.json` に記録し、未送信の行のみを送信して二重送信を防止すること。記録は既に存在しないファイル分を整理（prune）すること。書き込み中の最新ファイルへ追記された新規行もリアルタイムに送信できること |
| MQTT-05 | 自動送信: 有効かつブローカーIPが設定されているとき、`interval` 秒ごとにバックグラウンドで未送信の行を送信すること。送信処理はWebサーバー側の専用デーモンスレッドで行い、推論処理（`Picamera.py`）をブロックしないこと |
| MQTT-06 | 手動送信: Web上の「今すぐ送信」ボタンから未送信の行を即時送信できること。自動送信と手動送信の同時実行は排他制御し、後発はスキップすること |
| MQTT-07 | 最終送信時刻・結果・未送信行数をWebから取得して表示できること |
| MQTT-08 | 送信先（ブローカー）ホストの時刻にPiのシステム時計を同期する機能を備えること。送信先ホストのUDP123へSNTP（NTP）クエリを投げて時刻を取得し（純Python実装・追加ライブラリ不要、`Transmit Timestamp` を採用）、`sudo date -s @<epoch>` でシステム時計を設定すること（RTC搭載時は `sudo hwclock -w` も試行し、失敗は無視）。設定（`time_sync_enabled`、`time_sync_interval`、既定 `false`/`3600`）は `send_target_config.json` に永続化すること。時計変更にはroot権限を用いる |
| MQTT-09 | 時刻同期は、有効かつ送信先IPが設定されているとき、専用デーモンスレッドで起動時に1回＋`time_sync_interval` 秒ごとに自動実行すること。加えてWebの「今すぐ時刻同期」ボタンから手動実行できること。自動と手動の同時実行は排他制御し後発はスキップすること。最終同期時刻・結果（補正秒数・送信先時刻・エラー）をWebから取得して表示できること |

送信先設定ファイル（`send_target_config.json`）の形式:

```json
{
  "enabled": false,
  "host": "192.168.1.20",
  "port": 1883,
  "topic": "presence/record",
  "username": "",
  "password": "********",
  "interval": 600,
  "time_sync_enabled": false,
  "time_sync_interval": 3600
}
```

### 3.7 システム電源管理

| 要件ID | 要件内容 |
|-------|---------|
| PWR-01 | WebブラウザおよびタッチパネルからRaspberry Piをシャットダウン（`sudo shutdown -h now`）できること |
| PWR-02 | Web操作およびタッチパネル操作によるシャットダウン実行前に確認ダイアログを表示し、誤操作を防止すること |
| PWR-03 | シャットダウンコマンド送信後はWeb UIに「シャットダウン中...」を表示し、操作を無効化すること |
| PWR-04 | シャットダウン時は接続が切断されるため、APIのネットワークエラーを正常として扱うこと |
| PWR-05 | シャットダウン実行後は「シャットダウン中...」表示が消えないため、15秒後に画面全体を真っ黒にして電源断の見た目に合わせること。Web UIは最前面のブラックアウトを表示し、SPI LCDは「SHUTTING DOWN...」を15秒表示後に完全な黒画面にすること。SPI LCDのバックライトは電源直結でソフトから消灯できないため、ピクセルを黒にするのみとし、バックライトは点灯のままとすること（消灯はハードウェア制約により不可）|

### 3.8 SPI LCD・タッチパネル

#### 3.8.1 SPI LCD表示

| 要件ID | 要件内容 |
|-------|---------|
| LCD-01 | ILI9488コントローラの480×320 SPI LCDにカメラ映像とオーバーレイをリアルタイム表示すること |
| LCD-02 | カメラ映像はアスペクト比を維持してLCDに縮小表示すること |
| LCD-03 | FHD（1920×1080）モードでは映像（480×270）を画面上部に配置し、下部残余領域をタッチボタン領域とすること |
| LCD-04 | 640×640モードでは映像（320×320）を画面左端に配置し、右エリア（160px幅）を2列のボタン領域とすること。その他のモードでは映像を縦方向中央寄せし、余白領域をボタン領域とすること |
| LCD-05 | LCD表示はバックグラウンドスレッドで行い、推論ループをブロックしないこと |
| LCD-06 | IPアドレスを画面上部中央に常時表示すること（フォントサイズ0.7、シアン色・黒シャドウ付き、30秒キャッシュ更新） |

#### 3.8.2 タッチパネル操作

| 要件ID | 要件内容 |
|-------|---------|
| TCH-01 | XPT2046タッチコントローラをハードウェアSPI（spidev, SPI0 CS1）で読み取ること |
| TCH-02 | タッチ検出はIRQピン（GPIO 17）の立ち下がりを契機とし、50msポーリングで監視すること |
| TCH-03 | 同一ボタンへの連続反応を防ぐため、500msのデバウンス処理を行うこと |
| TCH-04 | タッチ座標はキャリブレーション値（X: 200〜3900, Y: 200〜3900）を用いてLCD画面座標に変換すること |
| TCH-05 | シャットダウンボタン押下時はLCD上に確認ダイアログ（「SHUTDOWN?」・「YES」・「NO」ボタン）を表示し、YES確定後にシャットダウンを実行すること。NO押下で通常画面に戻ること。YES確定後はLCDに「SHUTTING DOWN...」を表示し、15秒後に完全な黒画面にすること（PWR-05） |
| TCH-06 | モデル切り替え（OBJ/SIG）・解像度切り替え（640/FHD）ボタン押下時は、LCD上に確認ダイアログ（例: "MODEL: OBJ?"・"YES"・"NO"）を表示し、YES確定後のみ設定ファイルへの書き込みを実行すること。NO押下でキャンセルし通常画面に戻ること。シャットダウン確認ダイアログと同一レイアウト（YES: 左側青ボタン座標、NO: 右側緑ボタン座標）を使用すること |
| TCH-07 | LCD上部中央のIPアドレス表示部を2秒以上長押しすると、WPS（プッシュボタン方式）でWiFi設定を開始すること。`wpa_cli -i wlan0 wps_pbc` でWPS-PBCを起動し、接続確立（SSID付与）を最大120秒監視する。状態（「WPS: push router button」「WPS connecting...」「WPS OK」「WPS timeout」「WPS not available」）をIP表示の下にLCD表示すること。接続成功時は `wpa_cli save_config` で認証情報を永続化すること。WPSはwpa_supplicant直接管理時に有効で、NetworkManager運用環境では起動に失敗する場合がある |

#### 3.8.3 タッチボタン仕様

ボタンは「操作ボタン（5個）」と「設定ボタン（6個）」の2グループで構成し、カメラ解像度によってレイアウトが異なる。

**操作ボタン（5個）**

| ボタン | ラベル | 機能 |
|-------|-------|------|
| C- | C- | クロップ率をステップダウン（100→70→49→34→24→17→12→10%） |
| C+ | C+ | クロップ率をステップアップ（10→12→17→24→34→49→70→100%） |
| ID設定 | ID | シグナルタワーID領域をボタン押下後3秒間の検出収集で設定 |
| IDリセット | RST | 設定済みID領域を全削除 |
| シャットダウン | OFF | システムをシャットダウン |

**設定ボタン（6個）**

| ボタン | ラベル | 機能 |
|-------|-------|------|
| 物体検出モデル | OBJ | 物体検出モデルに切り替え（確認ダイアログあり、TCH-06参照） |
| シグナルタワーモデル | SIG | シグナルタワーモデルに切り替え（確認ダイアログあり、TCH-06参照） |
| 640×640解像度 | 640 | カメラ解像度を640×640に切り替え（確認ダイアログあり、TCH-06参照） |
| FHD解像度 | FHD | カメラ解像度を1920×1080に切り替え（確認ダイアログあり、TCH-06参照） |
| 結果保存切り替え | SVR | 結果画像保存のON/OFFトグル |
| 生画像保存切り替え | RAW | 生画像保存のON/OFFトグル |

**レイアウト仕様**

| カメラ解像度 | 操作ボタン配置 | 設定ボタン配置 |
|------------|-------------|-------------|
| 640×640 | 右エリア右列（80px幅 × 5段） | 右エリア左列（80px幅 × 6段） |
| それ以外 | 下部横5分割 | 上部横6分割（映像に重なる透明背景） |

- クロップステップは固定値リスト [10, 12, 17, 24, 34, 49, 70, 100] を使用し、C-/C+で前後の値に移動すること
- 設定ボタンは常時表示し、映像に重なる場合は透明背景（影付きテキスト）で表示すること

Webサーバーはポート8080でHTTP/GETリクエストを受け付ける。

| `GET /log_file_data` | `file=<ファイル名>` | 指定ログファイルの全エントリをグラフ描画用JSONで返す。応答形式: `{type: "signal_changes"\|"object_changes"\|"signal_log"\|"object_log", entries: [...]}` |
| `GET /image_files` | `type=result\|raw` | `/home/pi/images/`（result）または `/home/pi/raw_images/`（raw）内の画像ファイル一覧を返す（JSON: `{files: [{name, size, modified}]}`）|

| `POST /wifi_connect` | - | リクエストボディ `{"ssid": "...", "password": "..."}` でWiFiに接続する。レスポンス（`{"success": true}`）を先に返し、接続処理はバックグラウンドスレッドで1秒後に非同期実行する |
| `GET /ip_config` | - | 現在のIP設定を返す（JSON: `{interface, ip, prefix, gateway, dns, method}`）。`method` は `auto`（DHCP）または `manual`（固定）|
| `POST /set_ip_config` | - | リクエストボディ `{"mode": "static"\|"dhcp", "ip", "prefix", "gateway", "dns"}` でIP取得方式を設定する。`static` 時はIP・プレフィックス・ゲートウェイ・DNSをサーバー側でIPv4検証する。レスポンス（`{"success": true, "revert_sec": N}`）を先に返し、適用はバックグラウンドで1秒後に非同期実行する（IP変更で接続が切れるため）。固定IP適用後は `revert_sec` 秒以内に `/confirm_ip_config` で確認されなければ自動でDHCPに戻す |
| `GET /confirm_ip_config` | - | 固定IP設定の確認。新IPでページが読み込めた合図として呼ばれ、自動DHCP復帰タイマーをキャンセルする（JSON: `{success, pending}`）|

- 全APIはJSON形式でレスポンスを返すこと
- 全APIに `Access-Control-Allow-Origin: *` ヘッダーを付与すること

## 6. 非機能要件

### 6.1 性能

| 要件ID | 要件内容 |
|-------|---------|
| PERF-01 | 推論フレームレートは目標15FPSとする（IMX500のハードウェア制約を上限とする） |
| PERF-02 | Web配信用画像は1秒に1回更新すること |
| PERF-03 | 画像保存・CSVログ書き込みはバックグラウンドスレッド（SaveWorker）で行い、推論ループをブロックしないこと |
| PERF-04 | 設定ファイルI/OはSaveWorkerがバックグラウンドでポーリング（1秒間隔）し、メインスレッドはキャッシュを参照すること |
| PERF-05 | フレームキューの最大サイズは1（キャプチャスレッド）および3（保存キュー）とすること |
| PERF-06 | FHDモードのHDMIオーバーレイバッファは960×540（1/2スケール）とし、メモリ帯域幅を削減すること |

### 6.2 信頼性・安全性

| 要件ID | 要件内容 |
|-------|---------|
| REL-01 | 推論成功率（直近100フレーム）を常時監視し、異常を画面に表示すること |
| REL-02 | V4L2タイムアウトを防止するため、ファイルI/Oとsyscallをメインスレッドからオフロードすること |
| REL-03 | カメラ設定変更前にキャプチャスレッドを安全に停止すること |
| REL-04 | 認識OFFモードではDMAメモリ節約のためRAWストリームを無効化すること |
| REL-05 | プロセス終了時（KeyboardInterrupt含む）にカメラリソースを確実に解放すること |

### 6.3 設定永続化

| 要件ID | 要件内容 |
|-------|---------|
| CFG-01 | モデル設定・閾値・認識設定・保存設定は再起動後も保持されること |
| CFG-02 | 設定ファイルは `/home/pi/` 配下にJSON形式で保存すること |
| CFG-03 | モデル切り替え状態は `/tmp/model_status.json` に記録し、UIがポーリングできること |

## 10. 用語定義

| 用語 | 定義 |
|------|------|
| IMX500 | ソニー製ニューラルネットワーク処理機能内蔵CMOSイメージセンサー |
| RPK | Raspberry Pi Kernel形式のAIモデルファイル |
| NMS | Non-Maximum Suppression。重複する検出結果を除去するアルゴリズム |
| ScalerCrop | Picamera2のカメラ制御パラメータ。センサーのクロップ領域を指定する |
| DRM | Direct Rendering Manager。LinuxのHDMI出力制御インターフェース |
| SaveWorker | 画像保存・CSV書き込み・設定ポーリング・保存判定を担当するバックグラウンドスレッド |
| 推論ROI | IMX500が推論処理を行うセンサー上の領域（Region of Interest） |
| 点灯/点滅 | シグナルタワーの状態判定。直近45フレーム（3秒分）のバッファが満杯になった後、未検出が20%超で点滅（BLINK）、20%以下で点灯（ON）と判定。バッファ蓄積中は画面表示は点灯（ON）、CSVログは消灯（off）とする |
| クロップステップ | センサークロップ率の固定ステップ値。[10, 12, 17, 24, 34, 49, 70, 100]（単位: %） |
| ILI9488 | SPI接続の3.5インチTFT LCDコントローラ（480×320, 18bpp RGB666） |
| XPT2046 | SPI接続の抵抗膜式タッチパネルコントローラ |
