## 1. 背景

親1:子多の配備基盤（インベントリ・配布ドライバ・STA_NO重複検出）はCLIとして完成し、
実機2台で稼働している。しかし**子を増やす作業が `docs/DEPLOY.md` の10工程の手作業**であり、
順序を間違えると事故になる。

実際、2台目の投入時にSDカード完全コピーを起動した結果、次が同時に起きた:

- ホスト名が同一 → `child-csv-to-mqtt.py` の `client_id=f"child-csv-{DEVICE_ID}"` が衝突。
  MQTTは同一client_idの新規接続時に既存接続を切断するため、**2台が互いを蹴り合う無限ループ**。
  20秒間に `offline` を16回以上観測し、**元から動いていた1台目まで巻き込まれて**
  両方の送信サービスがクラッシュと再起動を反復した。
- STA_NO も同一 → 送信が安定していればOracleのMERGEキーに `device_id` が無い以上、
  レコードが無警告に欠落していた。
- mDNS名も奪い合い、既存機のavahiが衝突回避で自分を自動改名していた。

手順書は整備したが、**手順書は読まれない前提で設計すべき**である。本UIは、
危険な順序をUIの構造として強制することで、手順の記憶に依存しない増設を可能にする。

## 2. ゴール / 非ゴール

**ゴール**
- 今どの子がAPに繋がっていて、どの状態かを一目で見られる。
- インベントリに無い端末（＝新機）を自動で検出する。
- 新機の登録を、危険な順序を守ったまま画面から実行できる。
- 同名クローンでも**どの個体を操作しているか**が常に明示される。

**非ゴール（意図的に外す）**
- **STA_NOの設定**。子のWeb UIが担う。どの信号灯を映しているかは現場でしか判断できず、
  UIに持たせても値を知る手段が増えるわけではない。
- **アプリ/モデルの配布**。`scripts/deploy-fleet.sh` のままとする。壊れたときの影響が
  最も大きい操作をWebから叩けるようにする利得が薄い。
- **認証機構**。§4のとおりローカル限定とし、SSHの鍵を認証とする。
- 親自身の管理（docker compose の操作など）。

## 3. 前提

1. 親は wlan0（社内側）と wlan1（AP `10.42.0.1/24`）の2面を持つ。子はAP配下。
2. 親から子へは `pi` の鍵でSSHでき、子の中では sudo がパスワード無しで通る。
3. 子のアプリは `~` 直下の素python + systemd（`picamera` / `web_server` /
   `child-csv-to-mqtt`）。子のWeb UIは `:8080`。
4. インベントリは `fleet/children.conf`（1行1台、SSH到達名のみ、IPは書かない）。

## 4. アーキテクチャ

親のホスト上で `pi` として動く単一のPythonプロセス。stdlib の `http.server` を使い、
新規依存を増やさない（子の `web_server.py` と同じ作り）。systemd で常駐させる。

```
  操作者のPC ──ssh -L 8090:localhost:8090──▶ 親Pi
                                              │ 127.0.0.1:8090 (bind はここだけ)
                                       [fleet_ui プロセス / 実行ユーザ pi]
                                              │
                        ┌─────────────────────┼─────────────────────┐
                   ip neigh (wlan1)      ssh/scp で子へ        children.conf 読み書き
                   ARPで端末列挙          6工程を実行            インベントリ更新
```

**`127.0.0.1` にのみ bind する。** この画面は子へ SSH+sudo できるため、
ネットワークに露出させない。操作者は SSHトンネル越しに見る。SSHの鍵がそのまま認証になり、
独自の認証機構を作らずに済む。子のWeb UIが認証を持たないまま `0.0.0.0` で待ち受けている
問題を、こちらで繰り返さない。

**親側では sudo を一切使わない。** `ip neigh` の読み取り、`~/.ssh/known_hosts` への追記、
`fleet/children.conf` の編集はいずれも `pi` の権限で足りる。sudo が要るのは子の中だけで、
それは既存のSSH経路で通っている。

### 4.1 なぜ docker ではないのか

AP配下の端末一覧（ARPテーブル）は**ホストレベルの情報**で、通常のbridgeネットワーク上の
コンテナからは見えない。`network_mode: host` にすれば見えるが、加えて `~/.ssh` のマウントと
コンテナ内からのssh実行という摩擦が生じる。得るものに対して代償が大きい。

## 5. モジュール構成

1ファイルに詰めず、責務ごとに分ける。

| ファイル | 責務 | テスト方法 |
|---|---|---|
| `fleet_ui/discovery.py` | ARP出力とインベントリの突き合わせ。**純ロジック**（I/Oを持たない） | pytestで直接 |
| `fleet_ui/provision.py` | 登録6工程。1工程＝1関数。コマンド実行はここに閉じる | 偽ssh（既存の `fake_bin`）で |
| `fleet_ui/collect.py` | 子の稼働状況の収集（サービス状態・モデル・readiness・STA_NO割当） | 偽ssh/偽curlで |
| `fleet_ui/server.py` | HTTPの配線のみ。ロジックを持たない | ルートのJSONを検証 |
| `fleet_ui/static/index.html` | 画面。依存なしの素のJS（fetchのみ） | — |
| `fleet_ui/tests/` | 上記のテスト。`pyproject.toml` の testpaths に追加 | — |

`scripts/lib/sta_no_report.py` は **import して再利用**する。重複検出を書き直さない。

## 6. 識別子：なぜ MAC を主キーにするか

- **IP は変わる**。子は親APのDHCPで払い出され、再起動で変わり得る。
- **ホスト名は衝突する**。SDカードのコピーで増設すると2台が同名になる。これは仮定ではなく
  実際に起きた。
- **MAC は個体に固定**され、クローンでも複製されない。

したがって画面上の行は MAC を主キーとし、IPとホスト名は「現在の値」として併記する。
**登録中の操作はIP指定で行う**（ホスト名指定だとクローン2台のどちらを触っているか
判別できない）。

### 6.1 インベントリの解決には2経路が要る

インベントリのエントリからIPを得る方法は1つではない。実機で確認した結果:

| エントリ | 解決方法 |
|---|---|
| `pizero2w-2.local` | mDNS（`getent hosts`） |
| `zero2` | `~/.ssh/config` の別名。`ssh -G zero2` の `hostname` 行から取る |

両方を試し、得られたIPからARPテーブル経由でMACを引く。

なお `zero2` の ssh_config は `HostName 10.42.0.52` と**IPをハードコード**している。
この子のIPが変わればこの対応付けは壊れる。UIは解決に失敗した場合、その旨を
「対応付け不明」として表示し、黙って新機扱いにはしない（既存の子を新機と誤認すると、
登録ウィザードで稼働中の機体を再プロビジョニングしかねない）。

### 6.2 新機の判定

**APのARPに居るが、インベントリのどのエントリのMACとも一致しない端末**を新機候補とする。

## 7. 画面

1ページ。2つの領域のみ。

**上段：フリート一覧**（インベントリに載っている子）

| 列 | 内容 |
|---|---|

| IP / ホスト名 | 現在の値 |
| picamera / web_server | `systemctl is-active` |

MAC・IP・（分かれば）ホスト名と「登録する」ボタン。

## 8. 登録ウィザード（6工程）

`docs/DEPLOY.md` の10工程のうち、1（既存確認）は一覧表示そのもの、2（電源投入）は物理作業、
9〜10（STA_NO設定と掃除）は非ゴールのため、UIが担うのは6工程。

| # | 工程 | 実行内容 | 実行場所 |
|---|---|---|---|
| 1 | 送信を止める | `sudo systemctl stop child-csv-to-mqtt` | 子 |
| 2 | STA_NOを退避して空に | `id_names_config.json` をバックアップ後、全regionを空へ | 子 |
| 3 | ホスト名変更＋再起動 | `hostnamectl set-hostname` ＋ `/etc/hosts` 更新 ＋ `reboot` | 子 |
| 4 | mDNSを正常化 | **インベントリ上の全子＋新機**の `avahi-daemon` を再起動 | 全子 |
| 5 | host keyを登録 | `ssh-keyscan` | 親 |
| 6 | インベントリに追加 | `children.conf` へ追記 | 親 |

**工程1を最初に置く理由**：クローンだとMQTTのclient_idが衝突し、2台が互いを蹴り合う。
この競合を止めるのが最優先で、STA_NOの是正より先に来る。

**新しいホスト名は操作者が入力する。** ウィザード開始時に1度だけ尋ね、工程3で使う。
UIは次を検証してから先へ進める:

- 空でないこと、`[a-z0-9-]` のみで構成され、先頭・末尾がハイフンでないこと（DNS/ホスト名の制約）
- **インベントリ上の既存の子と重複しないこと**。重複を許すと、まさに今回の事故
  （同名によるMQTT client_id 衝突）を再現してしまう
- 既定値として `<既存の共通接頭辞>-<次の連番>`（例: 既存が `pizero2w` / `pizero2w-2` なら
  `pizero2w-3`）を提示する。操作者は上書きできる

**各工程の表示**：実行するコマンド／対象のMACとIP／実行ボタン／結果（成功・失敗と出力）。
**自動では進まない**。押した分だけ進む。

### 8.1 工程3の後は MAC で追跡し直す

ホスト名変更と再起動でDHCPのIPが変わり得る。復帰後は**MACでARPを引き直して**新しいIPを
特定する。IPやホスト名を頼りにすると見失うか、最悪クローンのもう一方を掴む。
MACを主キーにした設計がここで効く。

再起動の完了は、対象MACがARPに再出現し、かつSSHが通ることで判定する。タイムアウトした
場合は失敗として表示し、再試行できるようにする。

## 9. 安全設計

1. **登録ウィザードはインベントリに載っていない端末しか受け付けない。**
   稼働中の子を誤って再プロビジョニングする事故を構造的に防ぐ。
2. **再起動（工程3）は明示的な確認を挟む。** 押し間違いの影響が最も大きい。
3. **`127.0.0.1` のみに bind。** ネットワークに露出させない。
4. **親側でsudoを使わない。** 権限の最小化。
5. **失敗したら止まる。** 自動で次へ進まない。出力を見せ、再実行か中断かを選ばせる。
6. **中断しても再開できる。** 途中で止めた端末は「APに居るがインベントリに無い」状態で
   一覧に残り、次に開いたときに続きから実行できる。
7. **runtime状態に触らない。** `send_target_state.json`・ログ・画像は一切操作しない。

## 10. エラー処理

| 事象 | 挙動 |
|---|---|
| SSHが通らない | その端末を「到達不能」と表示。登録ウィザードは開始できない |
| インベントリのエントリがIPに解決できない | 「対応付け不明」と表示。**新機扱いにはしない** |
| 工程が失敗 | そこで停止。コマンドの実際の出力を表示。再実行/中断を選べる |
| 再起動後に復帰しない | タイムアウトで失敗扱い。MACで待ち続ける秒数は設定可能 |
| ARPが空（APに誰も居ない） | 「AP配下に端末がいません」と表示。エラーにはしない |

## 11. テスト戦略

- **`discovery.py` は純ロジック**。ARPのテキストとインベントリの一覧を与えて、
  分類結果（既知・新機・対応付け不明）を検証する。偽物は不要。
  - 既知の子が正しく既知と判定される
  - MACが一致しない端末が新機と判定される
  - IPに解決できないエントリが「対応付け不明」になり、新機扱いされない
  - 同名クローン2台がMACで区別される
- **`provision.py` は偽ssh**（既存の `scripts/tests/conftest.py` の `fake_bin` と同方式）で、
  各工程が正しいコマンドを正しい対象へ発行することを検証する。
  - 工程が失敗したら非ゼロで返り、次へ進まない
  - 対象がIPで指定されている（ホスト名でない）
- **ホスト名の検証**は純ロジックなのでpytestで直接。
  - 既存の子と重複する名前を拒否する（同名によるclient_id衝突の再現を防ぐ）
  - 不正な文字・先頭末尾のハイフンを拒否する
  - 既定値が既存の連番の次になる（`pizero2w` / `pizero2w-2` → `pizero2w-3`）
- **`collect.py`** は偽ssh/偽curlで、`/model_status` から `model_type` と `status` の
  両方を読むことを検証する（`/current_model` を見ないこと）。
- **`server.py`** は薄い配線なので、主要ルートが期待するJSONを返すことのみ確認する。
